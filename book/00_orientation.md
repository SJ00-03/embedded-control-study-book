# 00. 임베디드 제어 SW 학습 로드맵과 클라우드 친화 워크플로

이 lesson은 앞으로 이 저장소를 어떻게 사용할지 정하는 출발점입니다. 목표는 단순히 문법을 많이 아는 것이 아니라, Python·C·STM32·ROS 2·MATLAB/Control을 연결해 “측정하고, 판단하고, 제어하고, 검증하는” 임베디드 제어 소프트웨어 개발 역량을 만드는 것입니다.

## 1. 학습 목표

이 lesson을 마치면 다음을 설명할 수 있어야 합니다.

- 임베디드 제어 SW 직무에서 Python, C, STM32, ROS 2, MATLAB/Control이 각각 어떤 역할을 하는지 이해한다.
- Codex Web과 GitHub Pull Request 기반으로 학습서를 한 lesson 또는 한 lab씩 확장하는 이유를 설명한다.
- 클라우드 친화 학습 환경과 로컬 하드웨어 실습의 경계를 구분한다.
- 안전 중요 소프트웨어 관점에서 문서화, 테스트, 검토, 추적성이 왜 중요한지 이해한다.
- 학습 결과를 포트폴리오로 연결하기 위한 저장소 운영 방식을 계획한다.

## 2. 왜 이 개념이 임베디드 제어 SW에서 중요한가

임베디드 제어 SW는 하나의 언어나 도구만으로 완성되지 않습니다. 실제 개발 흐름에서는 C로 MCU 펌웨어를 작성하고, Python으로 로그를 수집하며, MATLAB/Control로 제어 응답을 분석하고, ROS 2로 상위 로봇 소프트웨어와 통신하는 식의 연결 작업이 자주 발생합니다. 따라서 “각 도구를 따로 공부하는 능력”보다 “역할을 나누고 인터페이스를 정의하는 능력”이 중요합니다.

또한 취업 준비 관점에서는 결과물을 재현 가능하게 보여 주어야 합니다. 면접관이나 리뷰어가 코드를 내려받아 빌드하고, README를 읽고, 테스트 결과를 확인할 수 있어야 합니다. 클라우드와 GitHub 중심의 저장소 구조는 이런 재현성을 높입니다. 특정 개인 PC, 특정 IDE, 특정 보드가 없으면 아무것도 확인할 수 없는 포트폴리오는 설득력이 약해집니다.

방산·로봇·안전 중요 SW 분야에서는 “작동했다”만으로 충분하지 않습니다. 요구사항을 어떻게 나누었는지, 위험한 입력을 어떻게 거부했는지, 테스트를 어떻게 남겼는지, 변경 이력을 어떻게 검토했는지가 중요합니다. 이 저장소는 그런 개발 습관을 lesson과 lab마다 반복하도록 설계합니다.

## 3. 기초 개념

### 임베디드 제어 SW의 기본 흐름

임베디드 제어 SW는 대체로 다음 흐름을 반복합니다.

1. 센서 또는 통신 입력을 읽는다.
2. 입력 데이터를 필터링하거나 해석한다.
3. 상태를 추정하거나 제어 명령을 계산한다.
4. PWM, UART, CAN, I2C, SPI 같은 인터페이스로 출력을 보낸다.
5. 로그와 테스트 결과로 동작을 검증한다.

이 흐름에서 C는 제한된 메모리와 시간 안에서 하드웨어 가까운 코드를 작성하는 데 쓰입니다. Python은 데이터 분석, 로그 처리, 테스트 자동화에 강합니다. STM32 학습은 MCU 주변장치와 실시간 실행 모델을 이해하게 해 줍니다. ROS 2는 로봇 시스템에서 노드 간 메시지 흐름을 구성하는 데 쓰입니다. MATLAB/Control은 시스템 응답, PID, 상태공간, 이산화 같은 제어 개념을 실험하는 데 유용합니다.

### 클라우드 친화 학습

이 저장소는 Codex Web과 GitHub에서 검토 가능한 산출물을 우선합니다. 그래서 모든 초기 C 실습은 Linux 환경의 GCC와 Makefile로 실행 가능해야 합니다. STM32, ROS 2, MATLAB 내용은 특정 데스크톱 설치를 전제로 하지 않고, 먼저 보드 독립 개념과 인터페이스 설계를 설명합니다.

### 한 PR에 하나의 학습 단위

한 번에 전체 책을 만들면 품질을 검토하기 어렵습니다. 대신 한 PR에서 하나의 lesson 또는 하나의 lab만 다루면 변경 범위가 작아지고, 테스트와 리뷰가 쉬워집니다. 이 방식은 실무의 작은 변경 단위, 코드 리뷰, 회귀 테스트 문화와도 연결됩니다.

## 4. 공식 또는 이론의 유도/직관

이 orientation에서 중요한 “공식”은 수학 공식이라기보다 학습 루프입니다.

```text
개념 이해 → 작은 구현 → 실행/측정 → 디버깅 → 문서화 → 다음 개념으로 확장
```

임베디드 제어 SW에서는 이 루프가 특히 중요합니다. 제어 이론을 알더라도 구현이 잘못되면 시스템은 불안정해질 수 있습니다. 반대로 코드만 작성하고 측정하지 않으면 실제 응답이 의도와 맞는지 알 수 없습니다.

또 하나의 직관은 계층 분리입니다.

```text
제어 목표
  ↓
알고리즘 및 상태 정의
  ↓
소프트웨어 모듈 인터페이스
  ↓
하드웨어 또는 미들웨어 연결
  ↓
로그, 테스트, 문서화
```

초보자는 종종 “보드에서 LED가 켜졌다” 또는 “노드가 실행됐다”에서 멈춥니다. 하지만 실무에서는 왜 그런 구조가 필요한지, 입력과 출력이 무엇인지, 실패 시 어떤 값을 반환하는지, 테스트로 무엇을 보장하는지를 설명해야 합니다. 이 저장소의 lesson 구조가 매번 “왜 중요한가”, “실무형 예시”, “디버깅 포인트”, “포트폴리오 연결”을 요구하는 이유가 여기에 있습니다.

## 5. 간단한 예시

예를 들어 DC 모터 속도를 제어하는 작은 프로젝트를 생각해 봅시다. 같은 주제라도 도구별 역할은 다릅니다.

- C: 목표 속도와 현재 속도를 입력받아 PWM 듀티비를 계산하는 함수 작성
- STM32: 타이머 PWM 출력, 엔코더 또는 센서 입력, 주기적 제어 루프 구성
- Python: 시리얼 로그를 저장하고 속도 응답의 평균, overshoot, settling time을 계산
- MATLAB/Control: 1차 또는 2차 시스템 모델을 만들고 PID 파라미터 후보를 비교
- ROS 2: 상위 노드에서 목표 속도 명령을 보내고 상태 토픽을 구독

처음부터 실제 보드와 로봇을 모두 연결할 필요는 없습니다. 먼저 C 함수와 Python 로그 분석처럼 클라우드에서 검증 가능한 작은 단위부터 만들고, 나중에 하드웨어 연결을 붙이면 됩니다.

## 6. 실무형 예시

실무형 저장소 운영 흐름은 다음과 같습니다.

1. `progress_state.yml`에서 다음 학습 항목을 확인한다.
2. 해당 lesson을 `book/` 아래에 작성한다.
3. 필요한 경우 `labs/` 아래에 작은 실행 가능한 실습을 만든다.
4. lesson은 12개 필수 절을 모두 포함한다.
5. `scripts/check_lesson_quality.py`로 구조를 검사한다.
6. 실습이 있다면 빌드와 실행 결과를 확인한다.
7. PR 설명에 변경 파일, 실행 명령, 다음 학습 항목을 남긴다.

이 흐름은 단순한 글쓰기 규칙이 아니라 취업 포트폴리오의 신뢰성을 높이는 장치입니다. “무엇을 공부했다”보다 “어떻게 검증 가능한 산출물로 남겼다”가 더 강한 증거가 됩니다.

## 7. 직접 구현 실습

이 lesson에는 별도 코드 lab을 추가하지 않습니다. 대신 저장소 검증 실습을 수행합니다.

```bash
python3 scripts/check_lesson_quality.py book/00_orientation.md
python3 scripts/check_lesson_quality.py book/02_c/01_memory_pointer_basics.md
cd labs/c/01_pointer_memory_lab && make && ./main
```

직접 해 볼 일은 다음과 같습니다.

1. `README.md`를 읽고 저장소의 목적을 한 문단으로 요약합니다.
2. `ROADMAP.md`에서 자신에게 가장 약한 트랙을 하나 고릅니다.
3. `progress_state.yml`의 `next_lesson`과 `next_lab`이 무엇인지 확인합니다.
4. `book/02_c/01_memory_pointer_basics.md`와 C lab을 실행해 lesson과 lab이 어떻게 연결되는지 관찰합니다.
5. 다음 PR에서 만들고 싶은 lesson 후보와 그 이유를 짧게 기록합니다.

이 실습은 코드 작성보다 워크플로 이해가 목적입니다. 임베디드 개발에서도 프로젝트 구조, 빌드 방법, 테스트 방법을 먼저 파악하는 능력은 매우 중요합니다.

## 8. 디버깅 포인트

학습 저장소를 운영할 때 자주 생기는 문제는 다음과 같습니다.

- lesson이 12개 필수 절 중 일부를 빠뜨린다.
- 코드 예제가 특정 로컬 환경이나 IDE에 묶여 다른 사람이 실행하기 어렵다.
- README에는 실행 명령이 있지만 실제 명령은 실패한다.
- 실습 결과를 비교할 expected output 또는 검증 방법이 없다.
- 너무 큰 PR을 만들어 리뷰가 어렵다.
- 방산 또는 안전 중요 SW 관점을 언급하면서 구체적인 위해 가능 구현으로 넘어간다.

해결 방법은 작게 만들고 자주 확인하는 것입니다. lesson 하나를 작성한 직후 품질 검사 스크립트를 실행하고, lab 하나를 만든 직후 빌드와 실행 명령을 실제로 돌려야 합니다. README의 명령은 장식이 아니라 재현성 계약이라고 생각해야 합니다.

## 9. 방산/로봇 SW 관점에서의 주의점

방산·로봇 SW를 준비한다고 해서 민감하거나 위해 가능한 구현을 다룰 필요는 없습니다. 취업 준비와 포트폴리오에서 보여 줄 핵심은 신뢰성 있는 개발 습관입니다.

이 저장소에서 다루는 방산·로봇 관점은 다음 범위에 머뭅니다.

- 실시간 제약을 고려한 코드 구조
- 입력 검증과 오류 처리
- 테스트 가능한 모듈 인터페이스
- 변경 이력과 문서화
- 코딩 표준과 코드 리뷰
- 로그 기반 디버깅과 재현 가능한 실험

반대로 특정 작전 목적, 위해를 가능하게 하는 알고리즘, 민감한 운용 절차는 다루지 않습니다. 이 경계는 학습자의 안전과 프로젝트의 지속 가능성을 위해 필요합니다.

## 12. 포트폴리오 연결 아이디어

이 orientation lesson 자체도 포트폴리오의 시작점이 될 수 있습니다. 저장소 루트 README에 다음 요소가 명확히 보이면 리뷰어가 프로젝트의 방향을 빠르게 이해할 수 있습니다.

- 어떤 직무 역량을 목표로 하는지
- 어떤 학습 트랙을 어떤 순서로 진행하는지
- 각 lesson과 lab을 어떻게 검증하는지
- 안전 및 저작권 경계를 어떻게 지키는지
- 다음에 무엇을 만들 계획인지

첫 포트폴리오 목표는 거창한 완성품이 아니라 “작지만 검증 가능한 학습 단위가 꾸준히 쌓이는 저장소”입니다. 이후 Python 로그 분석, C 링 버퍼, STM32 PWM 개념, MATLAB PID 시뮬레이션, ROS 2 명령 노드가 추가되면 이 orientation은 전체 프로젝트를 설명하는 안내판 역할을 하게 됩니다.
