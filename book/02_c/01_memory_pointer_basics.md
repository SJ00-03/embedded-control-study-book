# C 01. 메모리 모델과 포인터 기초

C 언어를 임베디드 제어 SW 관점에서 배울 때 가장 먼저 넘어야 할 벽은 포인터입니다. 포인터는 문법 암기 문제가 아니라 “데이터가 메모리 어디에 있고, CPU가 그 주소를 어떻게 사용하며, 내가 작성한 코드가 하드웨어 접근과 어떤 관계를 갖는가”를 이해하는 도구입니다.

## 1. 학습 목표

이 lesson을 마치면 다음을 할 수 있어야 합니다.

- 변수의 값과 변수의 주소를 구분한다.
- 포인터 변수가 저장하는 것이 “다른 객체의 주소”임을 설명한다.
- `&`, `*`, 배열 이름, 포인터 산술의 기본 의미를 구분한다.
- 스택 메모리의 지역 변수 수명과 포인터 사용 시점을 연결해 생각한다.
- 임베디드 제어 코드에서 포인터가 센서 버퍼, 통신 패킷, 레지스터 접근에 왜 자주 쓰이는지 설명한다.
- 위험한 포인터 사용을 디버깅 관점에서 점검한다.

## 2. 왜 이 개념이 임베디드 제어 SW에서 중요한가

임베디드 제어 SW는 “계산 결과”만 다루지 않습니다. 센서에서 들어온 바이트, UART 수신 버퍼, ADC 샘플 배열, 모터 제어 파라미터, 주변장치 레지스터처럼 메모리 배치와 접근 시점이 중요한 데이터를 다룹니다. C에서 이런 데이터를 효율적으로 전달하려면 값을 통째로 복사하기보다 주소를 전달하는 경우가 많습니다.

예를 들어 100개의 센서 샘플을 평균 내는 함수를 만든다고 가정해 봅시다. 배열 전체를 함수에 복사하면 메모리와 시간이 낭비됩니다. 대신 배열의 시작 주소와 길이를 전달하면 함수는 원본 버퍼를 직접 읽을 수 있습니다. 이때 포인터를 제대로 이해하지 못하면 잘못된 주소를 읽거나, 배열 범위를 넘어가거나, 이미 수명이 끝난 지역 변수의 주소를 사용하는 문제가 생깁니다.

로봇이나 안전 중요 소프트웨어에서는 이런 실수가 단순한 프로그램 종료로 끝나지 않을 수 있습니다. 제어 주기가 밀리거나, 센서 값이 잘못 해석되거나, actuator 명령이 비정상적으로 계산될 수 있습니다. 따라서 포인터는 “어렵지만 시험에 나오는 문법”이 아니라, 실시간성과 신뢰성을 지키기 위한 기본기입니다.

## 3. 기초 개념

### 값과 주소

C에서 변수는 어떤 타입의 값을 저장하는 이름 붙은 메모리 공간입니다.

```c
int speed_rpm = 1200;
```

`speed_rpm`은 값 `1200`을 담는 `int` 객체입니다. 이 객체는 메모리 어딘가에 놓입니다. `&speed_rpm`은 그 객체가 놓인 주소를 뜻합니다.

```c
int *p_speed = &speed_rpm;
```

`p_speed`는 `int`를 가리키는 포인터입니다. 즉 `p_speed`라는 변수 자체에도 값이 저장되는데, 그 값은 정수가 아니라 `speed_rpm`의 주소입니다.

### 역참조

포인터가 가리키는 객체의 값을 읽거나 쓰려면 `*` 연산자를 사용합니다.

```c
*p_speed = 1500;
```

이 문장은 `p_speed`가 가리키는 위치의 `int` 값을 `1500`으로 바꿉니다. 결과적으로 `speed_rpm`도 `1500`이 됩니다.

### 배열과 포인터

배열 이름은 많은 식에서 첫 원소의 주소처럼 동작합니다.

```c
int samples[3] = {10, 20, 30};
int *p = samples;
```

`p`는 `samples[0]`을 가리킵니다. `p + 1`은 바이트 주소에 1을 더한다는 뜻이 아니라, `int` 한 칸 뒤의 주소를 뜻합니다. 따라서 `*(p + 1)`은 `samples[1]`과 같습니다.

### 포인터와 수명

지역 변수는 일반적으로 함수가 실행되는 동안 스택 영역에 존재합니다. 함수가 끝난 뒤 그 지역 변수의 주소를 계속 사용하면 안 됩니다.

```c
int *bad_pointer(void) {
    int local = 42;
    return &local;  // 잘못된 예: 함수 종료 후 local의 수명은 끝난다.
}
```

이런 포인터는 댕글링 포인터가 됩니다. 운 좋게 동작하는 것처럼 보일 수 있지만, 그 동작에 의존하면 안 됩니다.

## 4. 공식 또는 이론의 유도/직관

포인터 산술의 핵심 직관은 “주소 + 원소 크기 × 인덱스”입니다. 타입이 `T *`인 포인터 `p`가 배열의 첫 원소를 가리킨다면 다음 관계를 생각할 수 있습니다.

```text
p + i  ≈  base_address + sizeof(T) * i
*(p+i) == p[i]
```

여기서 `≈`는 실제 C 문법의 포인터 연산을 바이트 주소 계산으로 직관화한 표현입니다. C 표준 관점에서는 같은 배열 객체 안에서의 포인터 연산만 정의된 동작입니다. 임베디드 개발자는 주소를 숫자처럼 보고 싶어질 때가 많지만, 일반 RAM 데이터에 대해 배열 범위를 벗어난 포인터 연산을 하면 정의되지 않은 동작이 될 수 있습니다.

메모리 접근을 제어 관점으로 비유하면 포인터는 “측정 채널 번호”와 비슷합니다. 센서 값 자체와 센서 채널 식별자는 다릅니다. 포인터 값은 데이터가 아니라 데이터 위치를 알려주는 식별자입니다. 식별자가 틀리면 제어 알고리즘이 아무리 정확해도 잘못된 입력을 읽게 됩니다.

## 5. 간단한 예시

아래 코드는 값 전달과 주소 전달의 차이를 보여 줍니다.

```c
#include <stdio.h>

void set_by_value(int x) {
    x = 100;
}

void set_by_pointer(int *x) {
    *x = 100;
}

int main(void) {
    int command = 10;

    set_by_value(command);
    printf("after value: %d\n", command);

    set_by_pointer(&command);
    printf("after pointer: %d\n", command);

    return 0;
}
```

`set_by_value`는 `command`의 복사본만 바꿉니다. 반면 `set_by_pointer`는 `command`의 주소를 받아 원본을 바꿉니다. 임베디드 코드에서 함수가 상태 변수나 출력 명령을 갱신해야 한다면 이런 주소 전달 패턴이 자주 사용됩니다.

## 6. 실무형 예시

센서 샘플 배열의 평균을 계산하는 함수를 생각해 봅시다. 실무 코드에서는 배열 시작 주소와 길이를 함께 전달해야 합니다. 포인터만 전달하면 함수는 배열이 몇 개인지 알 수 없습니다.

```c
#include <stddef.h>

int average_i32(const int *samples, size_t count, int *out_avg) {
    long sum = 0;

    if (samples == NULL || out_avg == NULL || count == 0U) {
        return -1;
    }

    for (size_t i = 0; i < count; ++i) {
        sum += samples[i];
    }

    *out_avg = (int)(sum / (long)count);
    return 0;
}
```

이 예시에는 몇 가지 실무 습관이 들어 있습니다.

- 입력 배열은 함수 안에서 바꾸지 않으므로 `const int *`로 받습니다.
- 배열 길이를 `size_t count`로 함께 받습니다.
- 출력 결과는 `int *out_avg`로 돌려주고, 성공 여부는 반환값으로 표현합니다.
- `NULL` 포인터와 `count == 0`을 먼저 검사합니다.

이런 패턴은 UART 패킷 파서, ADC 샘플 처리, 제어 파라미터 업데이트 함수에서 반복적으로 등장합니다.

## 8. 디버깅 포인트

포인터 문제가 의심될 때는 다음 순서로 점검합니다.

- 포인터가 `NULL`인지 확인합니다.
- 포인터가 가리키는 객체의 수명이 아직 유효한지 확인합니다.
- 배열 시작 주소와 길이가 함께 전달되는지 확인합니다.
- 반복문의 종료 조건이 배열 범위를 넘지 않는지 확인합니다.
- 입력 전용 데이터에 `const`를 붙여 의도치 않은 수정을 막았는지 확인합니다.
- 출력 포인터를 사용하기 전에 호출자가 실제 저장 공간을 제공했는지 확인합니다.

Linux cloud 환경에서는 `gcc -Wall -Wextra -Wpedantic` 같은 경고 옵션을 켜는 것이 첫 번째 방어선입니다. 더 깊은 검사가 필요하면 AddressSanitizer 같은 도구를 사용할 수 있지만, 이 저장소의 기본 실습은 가벼운 GCC 빌드를 우선합니다.

## 9. 방산/로봇 SW 관점에서의 주의점

방산 또는 로봇 SW에서 포인터 사용은 기능 구현 문제와 동시에 신뢰성 문제입니다. 잘못된 포인터는 잘못된 센서 값, 손상된 상태 변수, 예측 불가능한 제어 출력을 만들 수 있습니다. 따라서 포인터를 사용할 때는 “동작한다”보다 “검증 가능하다”를 기준으로 코드를 작성해야 합니다.

주의할 점은 다음과 같습니다.

- 함수 인터페이스에 입력, 출력, 길이, 오류 코드를 명확히 드러냅니다.
- `const`를 사용해 읽기 전용 입력을 표현합니다.
- 전역 버퍼를 여러 실행 흐름에서 공유한다면 동시 접근 규칙을 문서화합니다.
- 실시간 제어 루프 안에서는 불필요한 복사와 동적 할당을 피하고, 버퍼 수명을 명확히 관리합니다.
- 코드 리뷰 체크리스트에 포인터 유효성, 배열 경계, 수명, 소유권을 포함합니다.

이 lesson의 방산 관점은 안전 중요 SW 개발 규율, 검증, 문서화, 방어적 코딩에 한정됩니다.
